# Expo SDK 57 through a Vendored Expo SwiftPM Plugin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `rn-xtool doctor | build | install | start | run` work on `create-expo-app --template blank-typescript@sdk-57` projects (expo 57.0.31, react-native 0.86.3), with Expo 58 and bare 0.86.2/0.86.3/0.87.1/0.88.0 unchanged except for the listed generic fixes.

**Architecture:** An Expo version table says, per SDK, whether the project's own Expo SwiftPM plugin (58+) or a vendored copy of `expo@58.0.19` `scripts/spm` (shared patch plus vendored-only edits P1–P5) drives the build. SDK 57 runs on the bare driver path (`rn-spm-generate.js`, vendored RN scripts, the adapted 0.86.3 artifacts) with the vendored plugin, autolinking 58.0.15 and expo-modules-macros 0.22.0 as rn-xtool dependencies, and SDK 57's own precompiled ExpoModulesCore. A JSI step, moved before `rn-spm`, builds ExpoModulesJSI and synthesises the `ExpoModulesJSIHeaders.xcframework` SDK 57 does not ship.

**Tech Stack:** TypeScript (Node 20, ESM), vitest, CommonJS driver `scripts/rn-spm-generate.js`, vendored RN 0.88.0 scripts (`vendor/rn-spm`), vendored Expo 58.0.19 plugin (`vendor/expo-spm`, MIT 650 Industries), expo-modules-autolinking 58.0.15, expo-modules-macros 0.22.0, `plist`, xtool 1.23.0, Swift 6.4.

**Spec:** `docs/design/specs/2026-10-27-expo-sdk-57-design.md` (amendments at its end are binding; evidence: `docs/research/expo-57-vendored-plugin-spike.md`, `docs/research/compat-suite-proposal.md`; spike artefacts read-only under `<scratch>/spike57/`: `vendored-edits.diff`, `rnx-dist.diff`, `Spike57/.spike/`).

## Global Constraints

- Linux, Node 20+, Swift 6.4, xtool 1.23.0 unchanged; no CocoaPods, no Mac; `IOS_MIN` stays 16.4.
- `SUPPORTED_EXPO = { 57: { plugin: "vendored", pins: { expo: "57.0.31", "react-native": "0.86.3", "expo-modules-core": "57.0.24", "expo-modules-autolinking": "57.0.16", "expo-modules-jsi": "57.1.3" } }, 58: { plugin: "installed" } } as const` in `src/versions.ts`; SDK ≥ 58 keeps today's rule; `MIN_EXPO_SDK` goes.
- Exact rn-xtool dependencies: `"expo-modules-autolinking": "58.0.15"`, `"expo-modules-macros": "0.22.0"` (npm installs the host's `@expo/modules-macros-linux-{x64,arm64}` 0.22.0). rn-xtool's autolinking copy is not patched.
- Expo 58 and bare 0.86.2/0.86.3/0.87.1/0.88.0: same commands, same patches staged, same build steps, same driver/`setup-apple-spm.js` argv and env. Generated manifests change only by: the App importer flags when a scaffolded mixed library is autolinked (X6d), the importer marker in revision-2 scaffolded manifests (17), and X3/X6b/X6c in Expo-generated packages that hit them. Every task ends with the full `npm test` and `npm run lint` green; tasks touching fixtures, docs or vendor also run `npm run scan:private`.
- P1–P5 are vendored-only (`vendor/expo-spm/rn-xtool-edits.patch`); X3, X6b, X6c go in `patches/expo+58.0.19.patch`; fixes 14–17 in `patches/react-native+0.88.0.patch`. After a shared-patch change, `vendor/expo-spm` / `vendor/rn-spm` are re-derived and their provenance tests stay green.
- The vendored plugin resolves app packages (`@expo/config-plugins`, `xcode`) only from `RN_XTOOL_PROJECT_ROOT` (P2; unset → error), never by walking up from `vendor/`; it finds autolinking 58.0.15 and the macros through rn-xtool's `node_modules`.
- No edit to the user's `ios/`; SDK 57 does no xcodeproj injection. No `SPIKE_*` variables; every seam is a driver flag or an rn-xtool-set variable: `--expo-plugin`, `RN_SPM_EXPO_PLUGIN`, `RN_XTOOL_PROJECT_ROOT`, `EXPO_PRECOMPILED_MODULES_PATH`, `RN_XTOOL_REACT_HEADERS`, `RN_XTOOL_DEPS_HEADERS`. Nothing is read from a 58 tarball at build time.
- Error texts in this plan are verbatim.
- Shared-patch tasks re-patch the reference app `../app` in place so the existing guard tests (`reverse-applies cleanly to the installed …`) stay meaningful: `patch -R -p1 -F0` with the previous committed patch (`git show HEAD:<patch>`), then `patch -p1 -F0` with the new one, run in `../app`; only `node_modules/{expo,react-native}/scripts/spm` change. Say so in the task report.
- Commits: Conventional Commits in English, ≤ 50 chars, no body, one logical change each; no scratch code. Tasks 13–17 are run by the controller with Willy (iPhone); implementers never need the device. A library that fails is fixed, never documented as broken without Willy's decision.

## Review Focus

1. An SDK 57 project where npm nests expo-modules-core, expo-modules-jsi or expo-modules-autolinking under another package must be gated on the copy the build resolves (core from `expo`, jsi from core), not on a hoisted stray (Task 2 test `reads each pin where the build resolves it`); and since patch-package patches only the top-level copy, a jsi the build resolves from anywhere else is refused (Task 2 test `refuses a nested expo-modules-jsi`).
2. ExpoModulesJSI rebuilt with a changed interface but the same jsi version (patch re-applied, Swift upgrade) must rewrite the headers xcframework; an interrupted synthesis must leave nothing the next build treats as current (Task 5 tests `rewrites when the interface changes` and `a failed synthesis leaves no stamped xcframework`).
3. A global install: the vendored plugin must load the app's `@expo/config-plugins` and `xcode`, not rn-xtool's 58 copies next to it (Task 1 test `P2 resolves app packages from RN_XTOOL_PROJECT_ROOT, never from vendor/`).
4. An SDK 57 project whose `rnArtifactsDir` points at raw, unadapted 0.86.3 slots must stop at `jsi` naming the missing headers directory, not fail deep inside `swift build` (Task 5 test `stops when the React Native headers are missing`).
5. `build --clean` on SDK 57 deletes `ios/` (adapted slot, `expo-precompiled`): the plan must re-run `rn-artifacts` and `jsi` before `rn-spm` (Task 6 test `expo 57 --clean re-creates artifacts and JSI headers before rn-spm`).
6. Before the final verdict the reviewer answers, hint-free: "Name three ways this fails in production that no test covers." Any answer not in the spec's failure table goes to Willy as a decision, not to the implementer as a fix.
